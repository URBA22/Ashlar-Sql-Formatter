# Ashlar — SQL Formatter (T-SQL)

A SQL formatter for Visual Studio Code with first-class T-SQL support and a code
style you can shape in detail: 135 settings covering casing, indentation,
wrapping, clause layout, expressions, procedural code and DDL.

It is a hand-written tokenizer and layout engine with no external formatting
library, so behaviour on SQL Server syntax (`[bracketed names]`, `@variables`,
`#temp` tables, `BEGIN TRY`, `MERGE`, `GO` batches) is owned rather than
approximated.

## Using it

Open a `.sql` file and run **Format Document** (`Shift+Alt+F`), or select some
SQL and run **Format Selection** (`Ctrl+K Ctrl+F`). Both go through the standard
VS Code formatting commands, so **Format on Save** picks it up too:

```jsonc
{
  "[sql]": {
    "editor.defaultFormatter": "kymos.ashlar-sql-formatter",
    "editor.formatOnSave": true
  }
}
```

## Default output

```sql
SELECT r.OrderId,
       r.PlacedAt,
       CASE
           WHEN r.LineTotal >= 1000 THEN 'large'
           ELSE 'small'
       END AS Bucket
FROM dbo.Orders r
    INNER JOIN dbo.Customers c ON c.CustomerId = r.CustomerId
WHERE r.PlacedAt >= @FromDate
    AND r.Status = 'open'
ORDER BY r.PlacedAt DESC;
```

## Browsing the settings

Run **SQL Formatter: Open Style Reference** from the command palette. It opens a
panel listing every setting, grouped by section, each shown as its default output
beside the output it produces when changed — generated by the formatter itself
rather than written by hand.

The panel is a live settings editor. Pick the scope you are editing — **User**,
**Workspace**, or the folder you are working in — and every control shows the
value in force there, with the ones set in that scope marked and resettable.
Hover a value to preview what it does; click it to save it immediately to that
scope's `settings.json`. Edits you make elsewhere, in the settings UI or in the
file itself, show up in the panel straight away.

At the bottom, a live preview formats one query with your complete style, so you
can see the whole thing rather than one setting at a time.

## The settings

Every setting lives under `sqlFormatter.`, and the id names the section it comes
from: `sqlFormatter.queries.select.wrapElements`,
`sqlFormatter.expressions.caseClause.alignThen`, and so on. 138 settings in all.

Four primitives repeat across the sections:

| Primitive | Values |
| --- | --- |
| **Place elements on** | `newLine`, `sameLine`, `asInCommon` |
| **Wrap elements** | `chop` (one per line), `chopIfLong` (one per line only when the list overflows), `wrapIfLong` (fill to the margin), `doNotChange` |
| **Place comma** | `toBegin` (hanging left of the column), `toEnd`, `auto` (whichever the source used), `asInCommon` |
| **Parenthesis triple** | `openingParenthesis` (`sameLine`/`indented`/`aligned`) × `elements` (`sameLineAligned`/`wrappedUnindented`/`wrappedAligned`/`wrappedIndented`) × `closingParenthesis` (`atTheEnd`/`underOpening`/`underElements`) |

Every value of every enum produces output of its own — the build refuses to
finish otherwise. Values can still coincide on a *particular* example, which is
inherent rather than a gap: `chop` and `chop if long` agree whenever a list is
too long either way, `asInCommon` resolves to whatever Common says, and `auto`
resolves to whatever the source already did. Where that happens the style page
says so under the control rather than leaving you to hunt for a difference.

### `case.*` — Case section

`keyword`, `builtInType`, `builtInFunction`, `customFunction`, `identifier`,
`alias`; each `upper` | `lower` | `preserve`. Quoted identifiers and string
contents are never re-cased.

### `indents.*` — Tabs and Indents section

`useEditorIndentation` (default on — takes tab width and tabs-vs-spaces from the
editor), `useTabCharacter`, `smartTabs`, `tabSize`, `indent`,
`continuationIndent`, `keepIndentsOnEmptyLines`.

### `wrapping.*` — Wrapping section

`rightMargin` (default 120), `keepLineBreaks`, `commentAtFirstColumn`.

### `queries.*` — Queries section

- `common` — `alignFirstWordOfClause` (`toLeft`/`toLeftWithIndent`/`toRight`),
  `placeClauseElementsOn`, `placeComma`, `collapseShortStatements`
  (`enabled`/`subqueriesOnly`/`disabled`), `keepElementsUnderSectionHeader`,
  `alignSectionElements`, `alignLineCommentsAtRightOfElements`
- `select` — placement, wrapping, comma, `newLineAfterAllDistinct`,
  `keepElementsOnOneLineIfUpTo`, `useAs`, `alignAs`
- `from` — placement, wrapping, comma, `wrapFirstJoin`, `wrapNextJoin`,
  `indentJoin`, `placeJoinInJoinOnlyQueriesUnder`, `alignJoinedTables`,
  `alignTableAliases`, `wrapOnUsing`, `placeOnUsingUnder`
- `where` — placement, wrapping, `placeTopLevelBooleanOperator`, `alignAs`
- `orderGroupBy` — placement, wrapping, comma, `alignAscDesc`
- `insert` — `placeIntoOnNewLine`, `placeIntoClauseElementsOn`,
  `placeValuesRowsOn`, the parenthesis triple, `wrapColumnsOrValues`,
  `placeComma`, `collapseShortMultiRowValues`, `alignMultiRowValues`
- `update` — placement, wrapping, comma, `alignEqualSign`
- `with` — placement, `wrapSubqueries`, comma, `alignAs`
- `subquery` — the parenthesis triple

### `expressions.*` — Expressions section

Spacing (`spaceBeforeOpeningParenthesis`, `spacesWithinParentheses`,
`spaceBeforeComma`, `spaceAfterComma`, `spacesAroundOperators`,
`spaceBetweenParenthesizedSubExpressions`, `alignOperandsInBinaryExpressions`)
and `caseClause` (`wrapWhen`, `indentWhenIfWrapped`, `wrapThen`, `alignThen`,
`alignElseUnderThenWhenThenAligned`, `alignEnd`, `keepNewLineAfterThenElse`,
`collapseShortClause`).

### `code.*` — Code section

`statements` (`wrapEveryStatement`, `keepBlankLinesInCode`,
`newLineAroundSemicolon`), `declaredVariables`, `routineArguments`, `block`
(`wrapThen`, `wrapElse`, `wrapInnerCode`, `indentThenAndElse`, `indentEnd`,
`collapseWhenShort`), `loops`.

### `ddl.*` — DDL section

The parenthesis triple plus `alignTypes`, `alignDefaults`,
`alignNullabilities`, `collapseWhenShort`, `wrapAlterInstructions`,
`alignAlterInstructions`, `constraints.*`, `schema.*` (`indentContent`, and the
minimum and maximum blank lines between declarations), `view.*`, `postfix.*`.

### A few worth trying

```jsonc
// River style: clause keywords right-aligned
"sqlFormatter.queries.common.alignFirstWordOfClause": "toRight",

// Columns under the keyword rather than beside it
"sqlFormatter.queries.common.keepElementsUnderSectionHeader": true,

// Leading commas
"sqlFormatter.queries.common.placeComma": "toBegin",

// Line up aliases, assignments and column types
"sqlFormatter.queries.select.alignAs": true,
"sqlFormatter.queries.update.alignEqualSign": true,
"sqlFormatter.ddl.alignTypes": true,
"sqlFormatter.ddl.alignNullabilities": true
```

## Dialects

| `dialect` | Quoted identifiers | Variables | Notes |
| --- | --- | --- | --- |
| `tsql` *(default)* | `[x]`, `"x"` | `@x`, `@@x` | Nested block comments, `N'…'`, `#temp`, `GO` batches |
| `postgresql` | `"x"` | `:x`, `$1` | `$tag$…$tag$` literals, `::` casts, nested block comments |
| `mysql` | `` `x` ``, `"x"` | `@x`, `?` | `#` line comments, backslash escapes in strings |
| `sqlite` | `"x"`, `[x]`, `` `x` `` | `:x`, `@x`, `$x`, `?` | |
| `oracle` | `"x"` | `:x` | |
| `standard` | `"x"` | `:x`, `?` | ANSI keywords only |

## Guarantees and limits

Two properties are enforced by the test suite across every fixture:

- **Token preservation** — formatting changes only whitespace and the casing it
  was asked to change; the token stream of the output matches the input.
- **Idempotence** — formatting formatted SQL is a no-op.

Both run over every fixture twice: once at the default width and once at a
narrow one, so the layout paths that only appear when everything has to break
are covered too.

Anything the formatter cannot classify is passed through with normalised spacing
rather than restructured, so unrecognised vendor syntax degrades to "tidied up"
instead of "mangled". Unterminated strings, comments and parentheses are
formatted without throwing.

Every setting listed above changes the output. The style reference page proves
it: the build regenerates each example by running the formatter, and fails if a
setting is missing from a group or if its demonstration value is the same as its
default. One setting, `indents.useEditorIndentation`, is applied by the editor
rather than the engine — it decides whether the tab width comes from your editor
settings — so it is marked as such on the page instead of being demonstrated.

Known limits:

- `caseClause.alignEnd: "withCase"` aligns `END` with the line that holds `CASE`
  rather than with the `CASE` column.
- `select.useAs` is the one setting that adds a token rather than moving one, so
  it is the one setting that changes the token stream when switched on.
- The `loops.*` settings apply to `LOOP` / `END LOOP`, which T-SQL does not have;
  use them with the PL/pgSQL or Oracle dialects.
- Scripts that omit statement terminators rely on a heuristic: a statement
  keyword that begins a new source line starts a new statement. Semicolons make
  this exact.

## Development

```bash
npm install
npm run build:page  # compile, then generate media/style-reference.html
npm run compile     # build to out/ only
npm test            # compile tests to out-test/ and run them
npm run watch       # incremental build
```

The style reference page is generated, not checked in. `tools/style-page/`
holds the template and the catalogue that groups the settings; the build runs
every example through the formatter and fails if a setting is missing from every
group or if a demo value is the same as its default. The same build emits
`build/artifact-page.html`, the standalone version published on the web.

Press `F5` in VS Code to launch an Extension Development Host.

The engine in `src/formatter/` has no dependency on the
`vscode` API:

```js
const { formatSql } = require('./out/formatter');
console.log(formatSql('select a,b from t where x=1', {
  dialect: 'tsql',
  queries: { common: { alignFirstWordOfClause: 'toRight' } },
}));
```

| File | Role |
| --- | --- |
| `tokenizer.ts` | Source text to tokens. Owns all quoting and comment rules. |
| `dialects.ts` | Per-dialect lexing rules and vocabularies. |
| `keywords.ts` | Keyword / function / data-type word lists. |
| `clauses.ts` | Clause phrase tables and statement-boundary detection. |
| `options.ts` | The style model and its defaults. |
| `formatter.ts` | Layout engine: element lists, parenthesis styles, alignment. |
| `printer.ts` | Line buffer, indentation, and the alignment-mark post-pass. |
| `../styleReference.ts` | The Style Reference webview panel and settings writer. |

## Contributing

Contributions are welcome, and bug reports are contributions. The formatter is
plain TypeScript with no external formatting library and no runtime
dependencies, so there is nothing to learn before changing it beyond the file
table above — `npm install && npm test` is the whole setup.

### Reporting a bug

Open an issue with the
[**Wrong formatting output**](../../issues/new?template=01-formatting-bug.yml)
template. The one thing worth spending time on is reducing the SQL to the
smallest snippet that still shows the problem: a snippet goes into the test
suite verbatim as a regression, so a reduced report is most of the fix.

Use [**Crash or extension problem**](../../issues/new?template=02-extension-bug.yml)
for an error notification or a command that does nothing, and
[**New setting, value or dialect**](../../issues/new?template=03-setting-request.yml)
for a style the formatter cannot currently produce — check the Style Reference
panel first, since the settings cover more ground than it looks.

### Fixing a bug

1. Add the offending SQL to the regressions section at the bottom of
   `TSQL_CORPUS` in `test/corpus.ts`. Token preservation and idempotence now
   cover it at both the default and the narrow right margin, which catches a
   whole class of layout mistakes without writing an assertion.
2. If the bug is about *where* something lands rather than about corruption, add
   an `expectOutput` case to `test/formatting.test.ts` under the section that
   owns the setting. Those tests read as input SQL beside the exact expected
   text, so the new one should look like its neighbours.
3. Make it pass. Most layout decisions live in `formatter.ts`; alignment that
   depends on lines that were not printed yet is resolved by the mark post-pass
   in `printer.ts`.
4. Run `npm test` and `npm run build:page`.

### Adding a setting

A setting exists in four places, and the build fails if you miss one:

| Where | What |
| --- | --- |
| `package.json` | The `contributes.configuration` entry, with its type, enum and description. |
| `src/formatter/options.ts` | The field on the style model and its default. |
| `src/formatter/formatter.ts` | The behaviour. |
| `tools/style-page/` | The group it belongs to and the value to demonstrate. |

Two rules the build enforces: a new default must leave existing output
unchanged, and every enum value must produce output different from the default
somewhere — a value that changes nothing is a value nobody can use. If your
demonstration value legitimately coincides with the default on one example,
pick a different example rather than relaxing the check.

### Pull requests

Small and focused beats comprehensive. Show the before and after output in the
description — it is the fastest way for a reviewer to agree with the intent.
The checks in [CI](.github/workflows/ci.yml) run the suite on Linux, Windows and
macOS against Node 20 and 22, and package the extension; a green run means the
publish path works too.
